\begin{abstract}
This document specifies the cryptography of the app's security core (the Rust crate \texttt{secure\_core}): goals, threat model, primitives and cipher suites, the key hierarchy, data at rest, synchronisation, device pairing and sharing. Draft 0.2 added what milestone M1 of MVP~1 implements: the libraries and parameters of suite~1, passphrase handling, the recovery key and the keyring file (\cref{sec:passphrase,sec:recovery,sec:keyring}). Draft 0.3 adds milestone M2: the journal, merging, compaction and encrypted files (\cref{sec:rest}). Draft 0.4 adds the hardening of milestone M8: what the finished app writes and logs, platform backups, and the assurance checks (\cref{sec:ondisk,sec:assurance}). Draft 0.5 adds the fixes from the security review of M8: compaction only with both keyring copies written, the slot of the keyring copy in use, what is wiped from memory, file modes, the picker's photo copies, and locking while the app is in the background. Draft 0.6 adds journal format~2, a binary encoding of the batches (\dref{D55}, \cref{sec:rest}). It turns the decisions and proposals of the project's decision log (\texttt{APPDESIGN.md}; identifiers such as \dref{D9} or \dref{P43}) into a precise design that can be reviewed, formally analysed and implemented. Everything not yet decided is marked \todo{like this}. The app's name is deliberately absent; it lives only in the app's \texttt{branding.json} (\dref{D35}).
\end{abstract}

\section{Scope and principles}

\begin{itemize}
  \item \textbf{Local-first, no server of ours} (\dref{D4}, \dref{D24}). Data is created, stored and analysed on the user's devices. It moves only directly between devices (peer-to-peer, files) or through storage the user controls (their own cloud storage or server, \dref{D15}). We never receive user data, not even encrypted.
  \item \textbf{Everything at rest and in transit is encrypted}, under keys that only the user's devices hold, protected by a passphrase set during the app's setup (\dref{D9}, \dref{D37}).
  \item \textbf{Quantum-safe} (\dref{D23}): symmetric primitives with 256-bit keys; public-key operations hybrid (classical and post-quantum) unless a scheme from the literature is required (\dref{D25}).
  \item \textbf{Crypto agility} (\dref{D25}, \dref{P46}): every ciphertext, key and signature names its cipher suite and format version, so algorithms can be replaced.
  \item \textbf{A small, separate core} (\dref{D26}): only the core sees keys; the user interface sees decrypted records for display, never key material.
  \item \textbf{Signal as the role model} (\dref{D28}, \dref{P47}): written specification, formal analysis, verified primitives where available, audits, reproducible builds.
\end{itemize}

\section{Security goals}

\begin{enumerate}[label=G\arabic*]
  \item \textbf{Confidentiality} of all user data (training logs, health and body data, photos, videos, notes, the profile) against anyone without the user's keys, including the user's storage provider and network attackers, now and against a future quantum computer (``harvest now, decrypt later'').
  \item \textbf{Integrity and authenticity}: undetected modification, reordering, truncation or forgery of records, sync batches and shares must be impossible.
  \item \textbf{Rollback detection}: a storage provider that serves old data must be detected by devices that have seen newer data.
  \item \textbf{Least disclosure in sharing}: a share reveals only the selected records and fields (\dref{D16}); write access is limited to what the owner granted (\dref{D18}).
  \item \textbf{Recoverability by the user alone}: with the passphrase or the recovery key, and nothing from us.
  \item \textbf{Metadata minimisation}: storage providers learn as little as possible (sizes, counts, timing), see \cref{sec:metadata}.
\end{enumerate}

\noindent\textbf{Non-goals.} Protection against malware with full control of an unlocked device; recovering data when both the passphrase and the recovery key are lost; hiding \emph{that} someone uses the app.

\medskip
\noindent All crates are pinned to exact versions and are pure Rust; the core itself forbids \texttt{unsafe} code. MVP~1 uses RustCrypto for all of suite~1 (\dref{D45}); the post-quantum public-key parts arrive with sync and sharing.

\noindent\textbf{BSI TR-02102-1} (version 2026-01, read 19 October 2026) recommends using post-quantum KEMs as hybrids, and post-quantum signatures ``grundsätzlich nur in Kombination mit einem klassischen Signaturverfahren'': the hybrid is valid only if all its signatures are, and its keys serve only the hybrid. Suite~1 follows both rules. The guideline doesn't list X25519, Ed25519 or ChaCha20-Poly1305, though, so suite~1 doesn't claim conformance with it \cite{bsi}.

\noindent\textbf{Suite identifiers.} Every encrypted object starts with a header $h = (\mathit{format\_version}, \mathit{suite\_id}, \ldots)$ that is bound as associated data, so it can't be changed without detection.

\noindent\textbf{Agility rules} (\dref{P46}):
\begin{itemize}
  \item A registry in the core lists the suites with their status: \emph{active}, \emph{decrypt-only} (broken, being migrated) or \emph{experimental}.
  \item Devices and share partners announce their supported suites in signed form and never accept a suite below a minimum (downgrade protection).
  \item Keys are layered (\cref{sec:keys}), so replacing an algorithm re-wraps keys first and re-encrypts data in the background.
  \item Schemes taken from the research literature (\dref{D25}), e.g.\ threshold schemes, may form the classical or the post-quantum part of a suite. Where the functionality allows, they are combined with an independent, well-studied scheme; otherwise they stand alone and stay \emph{experimental} until reviewed.
\end{itemize}

\begin{enumerate}
  \item \textbf{Setup} (\dref{D37}): the core generates $MK$, $RK$ and the first journal key $K_{j,1}$, each 256 random bits, and hashes the passphrase. Nothing is written to disk until the user has confirmed the recovery key; only then is the keyring written (\cref{sec:keyring}).
  \item \textbf{Passphrase slot}: with a random 128-bit salt $s$,
  \begin{align*}
    H &= \Argon(\mathrm{norm}(pw), s; m, t, p),\\
    K_{pw} \concat c_{pw} &= \mathrm{HKDF}\big(s, H, \str{secure\_core/v1/slot/passphrase} \concat 0 \concat \mathit{suite} \concat \mathit{vault\_id}\big),
  \end{align*}
  64 bytes split into a wrapping key and a commitment; $W_{pw} = \AEAD.\Enc(K_{pw}, n, MK, a_{pw})$.
  \item \textbf{Recovery slot}: the same with $RK$ in place of $H$ and the label \str{secure\_core/v1/slot/recovery}. $RK$ is 256 random bits, so no slow hash is needed.
  \item \textbf{Keys derived from $MK$}: $K_{\mathrm{keyring}} = \mathrm{HKDF}(\mathit{vault\_id}, MK, \str{secure\_core/v1/keyring} \concat 0 \concat \mathit{suite})$ wraps the journal keys; $K_{\mathrm{mac}}$ (label \str{secure\_core/v1/keyring/mac}) authenticates the keyring.
  \item \textbf{Journal keys are random, not derived} (\dref{P69}): each journal generation has its own key, stored wrapped in the keyring. Compaction writes the current state under a new key and deletes the old one, so deleted and overwritten values become unreadable even if old file blocks survive on flash memory --- \emph{unless} an attacker also has the passphrase and a surviving copy of the old keyring. Full secure deletion needs a key store that can really delete, such as the hardware keystore (\dref{P17}).
  \item \textbf{Device wrap} (\dref{P17}): later. In MVP~1 the passphrase is entered at every start (\dref{D44}).
  \item \textbf{Changes}: a new passphrase or recovery key re-wraps $MK$ in its slot only. The old slot may survive in flash leftovers, so a changed passphrase doesn't protect against someone who knows the old one \emph{and} has such a copy; that needs a new $MK$ and re-encryption \todo{offer ``re-key everything''}.
  \item \textbf{Optional secret key} (\dref{P18}): \todo{decide}.
\end{enumerate}

\noindent\textbf{Key handling (memory)}: keys exist only inside the core; the user interface receives opaque handles. Every 256-bit key is a \texttt{SecretKey} on the heap (so moves leave no stack copies) and is wiped when dropped (\texttt{zeroize}); decrypted plaintext comes back in wiped buffers, a batch's plaintext is encoded into a buffer reserved at its final size (padding included, so no reallocation leaves a copy behind; fixed 19 October 2026), and the values of the records held in memory (texts, numbers and UUIDs, including the core's file keys) are overwritten when the vault locks, as is the old copy of a record's fields when they grow (\dref{D55}); Debug output shows names but never values, keys, salts or commitments (security review of M8). Argon2id's 64\,MiB work area is supplied by the core and wiped after each hash, because \texttt{argon2} 0.6.0's own \texttt{hash\_password\_into} frees it without wiping (its \texttt{block.rs}, checked 18 Oct 2026). \emph{Not} wiped: the copies of the passphrase and the recovery key in Dart and in the bridge's transfer buffers, the records the app has received in Dart, and zxcvbn's internal copies during the strength check (HMAC and SHA-256 states are wiped since M8, through their \texttt{zeroize} features). Memory locking (\texttt{mlock}) is not used yet.

\section{Passphrases}
\label{sec:passphrase}

\begin{itemize}
  \item \textbf{Normalisation} $\mathrm{norm}(pw)$, applied identically when setting and entering: every whitespace character becomes U+0020 (RFC 8265's OpaqueString profile maps all non-ASCII spaces this way \cite{rfc8265}); then Unicode NFC, as both RFC 8265 and NIST SP 800-63B-4 recommend \cite{sp80063b}; then spaces at the start and end are dropped, which NIST allows as a ``limited allowance for mistyping''. Case and inner spaces are kept.
  \item \textbf{Rules} (\dref{P63}), checked by the core: 15 to 1{,}024 code points after normalisation, and a zxcvbn score of at least 3 of 4 \cite{zxcvbn} (zxcvbn evaluates the first 100 characters). The minimum is NIST SP 800-63B-4's 15 characters for single-factor passwords (\dref{D54}): its rule is meant for logins a server can throttle, and a copied keyring can be attacked offline, slowed down only by Argon2id. The app shows one of ten hints (too short, common password, keyboard pattern, \ldots). zxcvbn~3.1.1 can pick a different warning for the same input from call to call, because it walks hash maps and keeps the first of two equally cheap match sequences; its score did not vary in our tests, and a regression test checks that. Its dictionaries are English only: ``meinpasswort1234'' (``my password 1234'') scores~3 and is accepted (checked 19 October 2026) \todo{German word lists, or a higher score, before the German launch}.
  \item \textbf{Suggestions}: five words from EFF's long list (7{,}776 words), $\log_2 7776^5 \approx 64.6$ bits, separated by spaces, which phone keyboards type without switching layouts.
  \item \textbf{Argon2id parameters} (\dref{P60}): $m = 64$\,MiB, $t = 3$, $p = 4$, version 0x13, 32-byte output, 16-byte salt, no secret or associated data: RFC 9106's second recommended option \cite{rfc9106}. Measured on 18 Oct 2026: 122\,ms per hash on an AMD Ryzen 5 7540U (release build, lanes computed one after another), also 122\,ms for a full unlock through the bridge. Phones: \todo{measure, only with the owner's consent}; if low-end phones take over 2\,s, $t = 2$.
  \item \textbf{Bounds}: a keyring may only contain $19 \le m/\mathrm{MiB} \le 1024$, $2 \le t \le 10$, $1 \le p \le 8$; anything else is refused before any hashing, so a damaged or hostile file can't remove the cost or demand unbounded memory. The recovery key still opens such a vault.
  \item \textbf{Upgrade}: if a slot's parameters are weaker than the current ones in some respect and stronger in none, a successful unlock re-wraps $MK$ with the current parameters and a new salt --- but only if the slot that opened is the newest copy's slot, so a newer passphrase change is never undone.
\end{itemize}

\section{The recovery key}
\label{sec:recovery}

$RK$ is written as 56 characters of Crockford's Base32 \cite{crockford} in 14 groups of four: a version byte (1), the 32 key bytes and a CRC-16/IBM-3740 (polynomial 0x1021, initial value 0xFFFF; check value 0x29B1 \cite{crccat}) over both, $35 \cdot 8 = 280 = 56 \cdot 5$ bits. The CRC detects every error within 16 consecutive bits, so every single wrong character and every swap of neighbouring characters, before any decryption (the tests try all of them). Input ignores case, spaces and hyphens, and reads O as 0 and I, L as 1. The version byte makes every key start with ``0''. The key for $32 \times$\texttt{0xAB} is \texttt{06NT-QAXB-NENT-\ldots-NENT-PD4T} (a golden test, computed independently).

\section{Offline guessing}
\label{sec:offline}
\emph{Research of 19 October 2026; proposal \dref{P85}.} Whoever holds a copy of the keyring can guess passphrases offline. Such copies include:
\begin{itemize}
  \item a forensic image of a phone taken after its first unlock (Android keeps the file keys in memory from then on, and so does iOS for its default class \cite{jhu2021});
  \item a stolen backup;
  \item a synced copy in the user's cloud.
\end{itemize}
Argon2id only multiplies the cost of each guess.

\paragraph{Attack cost.} hashcat~7.0 measures 1{,}703 Argon2id guesses per second on one RTX~4090 at RFC~9106's second recommended setting with $p = 1$ \cite{hashcat7}. Ours uses $p = 4$ with the same memory and passes, and we assume that costs an attacker about the same (not measured). At \$0.34 per rented GPU hour that is about \$$5.5 \times 10^{-8}$ per guess; dedicated hardware may be 10 to 100 times cheaper (an assumption). zxcvbn's score~3, the gate of \cref{sec:passphrase}, means fewer than $10^{10}$ guesses \cite{zxcvbn}.
\begin{center}\small

\midrule

So Argon2id is the last line of defence. What protects a copy is the secret's entropy, or a second secret that the copy doesn't contain. ``meinpasswort1234'' passes today's gate (\cref{sec:passphrase}).

\paragraph{What the platforms offer apps.}
\begin{itemize}
  \item \textbf{Android:}
  \begin{itemize}
    \item Keystore keys can't be exported: an attacker ``might be able to use any app's Android Keystore keys on the Android device, but it can't extract them from the device'' \cite{androidks}. StrongBox, a secure element, is slower than the TEE.
    \item Apps get no hardware attempt counter. The key builder has no setting for a minimum time between operations or a number of uses per boot, and \texttt{setMaxUsageCount} ``will be enforced in software'' where the hardware lacks it \cite{kgps}. Only keys bound to the lock screen inherit its hardware throttling (Gatekeeper, Weaver).
    \item \texttt{setUnlockedDeviceRequired} limits a key to an unlocked device; it had bugs in Android 12--14.
  \end{itemize}
  \item \textbf{iOS} \cite{applesec}:
  \begin{itemize}
    \item The Secure Enclave holds P-256 keys for signing and key agreement.
    \item Passcode guesses are entangled with the device's UID and throttled by the Secure Enclave.
    \item ``This device only'' Keychain items are useless on another device.
    \item \texttt{NSFileProtectionComplete} drops a file's key about 10 seconds after locking; the default class keeps it after first unlock.
  \end{itemize}
  \item \textbf{Sloth} (PoPETs 2024) uses the secure element's HMAC ``to provide a strict rate limit on password guessing'', on about 96\% of iPhones and 45\% of Android phones \cite{sloth}. Root on the device can still use such keys there \cite{keydroid}.
  \item \textbf{NIST SP~800-63B-4} asks for 15 characters for single-factor passwords, and for the key of an extra keyed hash to be kept in hardware: ``brute-force attacks on the hashed passwords are impractical as long as the secret key value remains secret'' \cite{sp80063b}.
\end{itemize}

\paragraph{How others limit guessing.}
\begin{itemize}
  \item \textbf{1Password} mixes a 128-bit Secret Key into the derivation, so the data on its servers ``cannot be used in brute-force cracking attempts'' \cite{onepw}.
  \item \textbf{Signal} (SVR3), \textbf{WhatsApp} (an HSM backup key vault) and \textbf{Apple's iCloud Keychain} escrow destroy the key after a fixed number of wrong guesses on their servers \cite{svr3,whatsappbk,applesec}.
  \item \textbf{Bitwarden, Proton Pass, Standard Notes and Threema Safe} rely on the key-derivation function alone.
\end{itemize}

\paragraph{Proposal (\dref{P85}).}
\begin{enumerate}
  \item \textbf{A device-bound passphrase slot for daily unlock.}
  \begin{itemize}
    \item $A = \Argon(\mathit{pw})$ and $K_{\mathrm{pw}} = \KDF(A \concat \mathrm{HMAC}_{K_{\mathrm{hw}}}(A))$.
    \item $K_{\mathrm{hw}}$ is a non-exportable HMAC key in StrongBox where the phone has one, else in the TEE; on iOS, a Secure Enclave key agreement takes its place.
    \item It needs no user authentication, so the passphrase alone unlocks.
    \item The HMAC's input depends on the guess, so every guess needs the device. A copy of the files without the device can't be guessed at all.
    \item With root on the device, the attacker computes $A$ on GPUs and asks the hardware only for the HMAC, so guessing runs at the hardware's speed: fast in a TEE, slow in a secure element. Sloth stretches this with repeated secure-element operations \cite{sloth}.
    \item If the hardware key is lost (e.g.\ by a reset), the recovery-key slot still opens the vault.
  \end{itemize}
  \item \textbf{No passphrase-only slot ever leaves the device.}
  \begin{itemize}
    \item Synced copies and backups carry the recovery-key slot and, for convenience, a two-secret slot $\KDF(\Argon(\mathit{pw}), \mathit{SK})$.
    \item $\mathit{SK}$ is a 128-bit Secret Key kept on the user's devices and printed on the recovery sheet, as 1Password does.
    \item A new device gets $\mathit{SK}$ by QR code from another device or from the sheet.
  \end{itemize}
  \item \textbf{The gate.} With 1 and 2, the passphrase only has to resist guessing on the device. So 15 characters and zxcvbn's score~3 can stay, once German word lists exist. Where a passphrase alone protects data (the browser, a desktop without a hardware key), require an estimated $10^{15}$ guesses (about 50 bits) or a generated passphrase.
  \item \textbf{Hygiene:}
  \begin{itemize}
    \item keys are wiped when the vault locks (done, M8);
    \item no operating-system backups (\dref{D52});
    \item on iOS, \texttt{NSFileProtectionComplete} and exclusion from backups;
    \item the Argon2id parameters re-measured on real phones, only with the user's consent.
  \end{itemize}
  \item \textbf{Server-side guess limits} (an HSM or an enclave) would protect even weak passphrases off the device, but they need a server: \dref{O26}.
\end{enumerate}

\section{The keyring}
\label{sec:keyring}

The keyring file holds the two slots and the wrapped journal keys. Format~1, little-endian:

\begin{center}\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
Field & Content \\
\midrule
header (52 bytes) & magic \texttt{SCKEYRNG}, format (u16, 1), suite (u16, 1), $\mathit{vault\_id}$ (16), $\mathit{device\_id}$ (16), sequence number (u64, increases with every rewrite) \\
slots & count (u8, 2), then each: type (u8). Passphrase (1): salt (16), $m$, $t$, $p$ (u32 each), commitment $c_{pw}$ (32), nonce (24), $W_{pw}$ (48). Recovery (2): salt (16), $c_{rk}$ (32), nonce (24), $W_{rk}$ (48) \\
journal keys & count (u8, 1--8), then each: purpose (u8, 1 = journal), generation (u32), nonce (24), wrapped key (48) \\
MAC (32) & $\mathrm{HMAC}(K_{\mathrm{mac}}, \text{everything before})$ \\
checksum (32) & SHA-256 of everything before \\
\bottomrule
\end{tabularx}
\end{center}

\begin{itemize}
  \item \textbf{Associated data}: $a_0 = \texttt{SCKEYRNG} \concat \mathit{format} \concat \mathit{suite} \concat \mathit{vault\_id}$. Passphrase slot: $a_{pw} = a_0 \concat 1 \concat s \concat m \concat t \concat p \concat c_{pw}$; recovery slot: $a_{rk} = a_0 \concat 2 \concat s \concat c_{rk}$; journal key: $a_0 \concat \mathit{purpose} \concat \mathit{generation}$. A slot copied from another vault therefore opens nowhere (tested).
  \item \textbf{Key commitment}: XChaCha20-Poly1305 is not key-committing, so a ciphertext could be built that opens under two keys. Each slot stores a commitment derived together with its wrapping key \cite{albertini}; it is compared (in constant time) before decryption. A mismatch means ``wrong passphrase'' or ``wrong recovery key''; a match followed by a failed decryption means damage.
  \item \textbf{MAC}: once $MK$ is known, the HMAC authenticates every byte of the file, including the device identifier and the sequence number, which no AEAD covers.
  \item \textbf{Checksum}: unkeyed, so it protects against nothing; it only lets the app tell damage from a wrong passphrase before running Argon2id. Magic and format stay at the same offsets in every future format, so older apps can report ``made by a newer version''.
  \item \textbf{Two copies}: \texttt{keyring} and \texttt{keyring.2}, each replaced atomically (temporary file, \texttt{fsync}, rename, \texttt{fsync} of the folder). Changes write the main copy first; from then on they count. Opening tries the copies newest first, uses the newest copy whose MAC and journal keys verify under the opened $MK$, and rewrites the other copy if it differs. The secret must open that copy's own slot, not merely some copy's: after a change whose backup write failed, the backup still holds the old slot, and the old passphrase or recovery key must not work (M8). Tests flip every byte of one or both copies (with the checksum fixed up, as an attacker could): with both copies changed nothing opens, with one changed the other is used and the damaged one restored.
  \item \textbf{Crash safety}: tests simulate a crash at every step of the setup and of a passphrase change. Afterwards the setup either left no vault (and can simply be repeated) or a vault that opens with both secrets; a passphrase change leaves the old or the new passphrase working, with the same keys, and once the new one has opened the vault the old one no longer does.
  \item \textbf{Locking}: one open vault per folder, by an in-process registry and an operating-system file lock on \texttt{LOCK}.
\end{itemize}


\section{Data at rest}
\label{sec:rest}

\subsection{Records and the journal}
\label{sec:journal}
A record (set, session, measurement, \ldots) is a kind, an identifier (UUID version~7) and flat fields: numbers, text, booleans. The core knows nothing about what they mean. Draft 0.1 encrypted each record on its own; MVP~1 instead keeps an append-only encrypted \emph{journal} of operation batches (\dref{P59}), replayed into memory at unlock; the app queries in memory. Edits and deletions are new operations. Identifiers, kinds, field names and timestamps are all inside the ciphertext.

\noindent\textbf{The file} (one per generation $g$, \texttt{journal-}$g$\texttt{.log}, little-endian; formats~1 and~2 share this layout):
\begin{center}\small
\begin{tabularx}{\textwidth}{@{}lX@{}}
\toprule
header (32 bytes) & magic \texttt{SCJOURNL}, format (u16: 1 or 2), suite (u16), $\mathit{vault\_id}$ (16), generation $g$ (u32) \\
each frame & $\ell$ (u32), $\lnot\ell$ (u32), kind (u8, 1 = batch), $\mathit{device\_id}$ (16), $\mathit{seq}$ (u64), nonce (24), ciphertext with tag ($\ell - 49$) \\
\bottomrule
\end{tabularx}
\end{center}
A frame is $\AEAD.\Enc(K_{j,g}, n, \mathit{batch}, \mathit{header} \concat \ell \concat \lnot\ell \concat \mathit{kind} \concat \mathit{device\_id} \concat \mathit{seq})$, so it can't be moved to another vault, generation, device or position. $\mathit{seq}$ starts at 1 in every file and increases by one. The plaintext is a batch $\{\mathit{hlc}, \mathit{ops}\}$, at most 1\,MiB, padded to a multiple of 128 bytes. Operations: \emph{put} (set fields; others stay; \texttt{null} clears one), \emph{del} (a tombstone) and \emph{snap} (written by compaction, below).

\noindent\textbf{Format~2} (\dref{D55}, since 19 October 2026) encodes the batch in binary instead of JSON (MVP~1's format~1, padded with spaces):
\begin{itemize}
  \item \textbf{Tables per batch:} a table of the kinds and field names, and one of the devices that snapshot stamps refer to. Operations point into them, so every frame still decodes on its own.
  \item \textbf{One stamp per group:} a snapshot keeps one stamp per group of fields written together, instead of one per field.
  \item \textbf{Compact values:} ids and texts in canonical UUID form take 16 bytes. Integers are minimal LEB128 varints, negative ones stored as $-1-n$. Floats are 8 bytes and must be finite.
  \item \textbf{Zero padding,} instead of spaces.
  \item \textbf{Strict decoding:} counts are checked against the bytes left, indexes against the tables; varints must be minimal and texts UTF-8; names must be unique within a record; groups come in increasing stamp order; only zeros may follow the batch.
\end{itemize}
The format sits in the header, and the header is part of every frame's associated data, so a frame can't move to a file of the other format. Unlock reads both formats. A file keeps its format for appends, and a journal in format~1 makes compaction due, which rewrites it in format~2. Tests: round trips (also as property tests), the size bound used to split compaction batches, a golden file, refusal of every truncation and malformed field, random and damaged inputs without panics, and the migration from format~1.

\noindent\textbf{Growth over decades} (measured 19 October 2026, \dref{D55}). The journal stays close to the live data thanks to compaction, but unlock replays all of it into memory. With format~1, one strength session a day gave 8\,MB a year. After 10 years that meant 0.6\,s more to unlock on a desktop, and a store of 185\,MB in memory; after 50 years, 3.1\,s and 874\,MB (store sizes measured after unlock in a fresh process; the store is the same for both formats). Two causes:
\begin{itemize}
  \item every field carried its own merge stamp (about 70 bytes of JSON);
  \item the whole history is kept in memory.
\end{itemize}
The plan:
\begin{itemize}
  \item journal format~2 (above, done): 0.9\,MB a year, and unlock about twice as fast after 25 and 50 years; memory is unchanged;
  \item a compact store in memory (done): kinds and field names kept once, UUIDs in 16 bytes, one stamp per group of fields, values in a small type that can be wiped. After 10 years the store holds 73\,MB instead of 185\,MB, and unlock is twice as fast;
  \item archive segments per year (done in the core, below).
\end{itemize}

\noindent\textbf{Archive segments} (\dref{D55}, \dref{P95}, since 20 October 2026). At compaction, the records of each year that is two years old leave the journal for an archive file of that year; the current and the previous calendar year always stay in the journal. Unlock reads only the journal, so after 50 years of a daily session it adds about 50\,ms and 15\,MB on a desktop.
\begin{itemize}
  \item \textbf{A record's year} is the UTC year in which its UUIDv7 identifier was created. Records with other identifiers (fixed ones, the core's own) stay in the journal.
  \item \textbf{The file} has the journal's layout under the magic \texttt{SCARCHIV}, with the year where a journal has its generation. Its frames are sealed under a key $K_{a}$ of its own, fresh for every version of the file, with the header in the associated data. A frame can't move between archives, years or journals: the key, the magic or the year would differ.
  \item \textbf{The key} is a field of a record of the core's own kind \texttt{\_archive} in the journal, like the keys of files (\cref{sec:rest}); the keyring is unchanged. A new version of an archive gets a new file and a new key, and the record of the old key is left out of the new journal generation, so the old version is shredded with that generation's key (\dref{P69}).
  \item \textbf{Changes:} changing or deleting a record of an archived year loads that year first, so the app never sees half a record. The next compaction writes the year again under a new key; a deleted record is then gone from every file that still has a key.
  \item \textbf{Order of writes:} the new archive files first, then the keyring and the new journal as in every compaction. A crash in between leaves archive files whose keys exist only in memory; files no \texttt{\_archive} record names are removed at unlock and after compaction.
  \item \textbf{Damage:} an archive that doesn't read is refused as a whole. If the journal holds changes to its year, the vault opens read-only, because compaction would write the year from part of its records.
  \item \textbf{Clock:} if the clock was ahead and is set back, archives of years that aren't two years old any more are loaded at unlock, and compaction returns their records to the journal.
\end{itemize}
Summary records in the journal (bests, estimated 1RMs, weekly volume), kept by the app, are still to come \todo{summary records; how the app shows old years (O27)}.

\noindent\textbf{Nonces, and no encryption in place.} ChaCha20 is a stream cipher. Encrypting two different plaintexts under the same key and nonce would reveal their XOR, and Poly1305 would then allow forgeries. That is the classic problem of data at rest rewritten in place. The core never does it:
\begin{itemize}
  \item \textbf{Nothing is re-encrypted in place.}
  \begin{itemize}
    \item The journal only appends: an edit is a new frame, and compaction writes a new file under a new key.
    \item The keyring and the encrypted files are replaced as whole files and sealed again with fresh nonces.
  \end{itemize}
  \item \textbf{Every encryption draws a fresh random 192-bit nonce} from the operating system. A file's chunks use a random 128-bit prefix plus the chunk's index.
  \begin{itemize}
    \item With 192 bits, random nonces are safe: $n$ encryptions under one key repeat a nonce with a probability below $n^2/2^{193}$, i.e.\ $2^{-97}$ for $2^{48}$ frames.
    \item There are no counters, which a crash, a restored backup or a vault copied to two devices could repeat.
  \end{itemize}
  \item \textbf{Keys are short-lived:} one per journal generation, one per file, one per sealed container (\cref{sec:sealed}). Even a repeated nonce would stay within one key's lifetime.
  \item \textbf{Identical ciphertexts appear only where nothing changed,} e.g.\ the two keyring copies, or a slot carried over unchanged. They reveal just that.
\end{itemize}
Disk encryption needs XTS or wide-block modes because a sector has no room for a nonce and a tag; our frames carry both (40 bytes), so a randomized AEAD fits. An observer of successive versions (the user's cloud, two forensic images) still learns sizes (padded to 128 bytes), when and how many frames were added, and which files exist. Tests check that edits only append, that no frame repeats a nonce, and that a file sealed twice gets fresh nonces.

\noindent\textbf{Commit}: validate everything first; encrypt the batch; append it in one write and \texttt{fsync} it; only then apply it in memory. If the append fails, the partial frame is cut off again; if even that fails, the vault refuses further changes until it is reopened, because a new frame behind garbage would look like damage.

\noindent\textbf{Reading}: a crash can leave only an unfinished or garbled \emph{last} frame (a prefix of the append, or zeros where the file grew but the data didn't arrive). That is a \emph{torn end}: it is cut off and reported (\texttt{recovered\_journal}). Anything wrong before the last frame --- a frame that doesn't decrypt, a sequence gap or repetition, a frame of another device --- is \emph{damage}: the vault opens read-only with the batches before it, and nothing is deleted. The complement $\lnot\ell$ keeps the two apart: without it, one flipped bit in an early frame's length could make all later frames look like one unfinished last frame, and they would be cut off. With it, every single-bit change before the last frame is reported as damage (tested for every bit of a frame). Dropping whole frames at the end can't be detected locally (no rollback protection on one device).

\noindent\textbf{Merging} (\dref{P22}--\dref{P25}): every write has a stamp $(\mathit{hlc}, \mathit{device\_id}, \mathit{seq}, \mathit{index})$, ordered lexicographically; $\mathit{hlc}$ is a hybrid logical clock (milliseconds in the upper 48 bits, a counter in the lower 16) that only increases, even when the device clock is set back. Per field the highest stamp wins; a record is visible if its latest put is newer than its latest deletion, and only fields written after the deletion are visible. Merging is commutative and idempotent (property tests over random histories from two devices, shuffled and duplicated).

\noindent\textbf{Compaction with crypto-shredding} (\dref{P69}), from generation $g$ to $g + 1$:
\begin{enumerate}
  \item Add a fresh random key $K_{j,g+1}$ to the keyring. Both copies must be written; if the backup copy can't be, compaction stops here, so a damaged main copy can never leave the new journal without its key (M8).
  \item Write \texttt{journal-}$(g{+}1)$\texttt{.log} atomically: the visible records only, as \emph{snap} operations that keep each surviving value's original stamp (so a later merge with other devices stays correct), in batches of about 256\,KiB. Deleted records and overwritten or deleted values are left out.
  \item Switch to generation $g + 1$ in memory. From here on it counts: if writing the file reported an error but the file might exist, the core removes it or refuses further changes, because the next unlock would otherwise read it and miss later commits.
  \item Remove $K_{j,g}$ from the keyring, then the old file. If this fails, compaction stays due until the next attempt or unlock has finished it.
\end{enumerate}
Unlock uses the newest generation that has both a file and a key, and finishes an interrupted compaction by removing other keys and \emph{older} files. A journal file newer than every key held means the keyring copy in use is older than the data (e.g.\ a restored or stale copy): the vault opens read-only and nothing is deleted (M8). Tests crash at each of the 26 steps; afterwards the vault always shows the same records, holds exactly one key and one journal, and takes new commits. Single-device simplification: compaction drops tombstones too; with sync they must be kept until every device has seen them \todo{tombstone retention with sync}. When to compact: the core reports it as due after any deletion or when overwritten values outnumber live ones two to one; the app compacts after a deletion's undo window has closed and before locking.

\subsection{App settings}
App settings (units, language, theme, timer defaults and alarms, enabled areas) describe how the app behaves, not the athlete. They are stored unencrypted on the device (\dref{D39}), which also lets the app show the right language before it is unlocked. When synced they travel inside the encrypted sync batches like any record (\dref{P58}). Anything that describes the person (profile, weight class, sports) is a record and encrypted.

\subsection{Large files: photos and videos}
\label{sec:blobs}
Each file has a random identifier $\mathit{fid}$ (128 bits) and its own random key $K_f$, kept in a core-internal record of the journal (invisible to the app), so deleting the file's record and compacting destroys the key like any other value. File format~1, \texttt{blobs/}$\mathit{fid}$\texttt{.blob}: a 64-byte header (magic \texttt{SCBLOBFL}, format, suite, $\mathit{vault\_id}$, $\mathit{fid}$, chunk size, a random 16-byte nonce prefix $p$), then the file in chunks of 64\,KiB; chunk $i$ is $\AEAD.\Enc(K_f, p \concat i_{\mathrm{BE64}}, \mathit{chunk}_i, \mathit{header} \concat i \concat \mathit{is\_last})$, all full-size except the last; an empty file is one empty last chunk. Chunks can be decrypted on their own (seeking in videos later, \dref{P34}) while reordering, truncation, appending and moving to another vault or file are detected (tested). The file is written atomically before its key is committed; unlock removes files without a key (left by a crash in between). Photos are re-encoded by the app before storing, which removes location and other metadata (\dref{D43}).

\subsection{What is on disk}
\label{sec:ondisk}
The vault folder holds \texttt{LOCK}, \texttt{keyring}, \texttt{keyring.2}, one \texttt{journal-}$g$\texttt{.log} and \texttt{blobs/}. A test fills a vault with marked values (a name, notes, a photo), compacts, writes more, and searches every file for the markers and for field and kind names: none appears.

The same holds for the finished app (M8). Its end-to-end test runs setup, logging, two passphrase changes, a new recovery key and a recovery through the real core, then writes a marked name and notes. It searches every file the app wrote (the vault, \texttt{settings.json} and, on Android, the app's cache) for the marker, all three passphrases, both recovery keys and the field names, in UTF-8 and UTF-16: none appears. The security review found one file this search missed, because the test never used the real photo picker: the Android picker plugin left a full copy of every picked photo, with its location data, in the cache. The app now deletes that copy after reading it, and clears leftovers at every start. \texttt{settings.json} holds exactly its six keys, and neither the app's own log nor the Android system log contains any of the secrets.

\paragraph{Platform backups.} On Android the app opts out of cloud backup and of device-to-device transfer (\dref{D52}). It sets \texttt{allowBackup="false"} and adds rules that exclude every storage domain, for Android~12 and later and for Android~11 and earlier, because \texttt{allowBackup} alone doesn't stop device-to-device transfers on all devices for apps targeting Android~12. The encrypted vault would be safe in a backup; the point is that nothing leaves the device without the user's action. A release check verifies the merged manifest, and that the app holds no \texttt{INTERNET} permission. On Linux and Android the vault folder and its files are for their owner only (modes 0700 and 0600); on Android the app's private folder is closed to other apps anyway.

\paragraph{Locking while away.} The app locks five minutes after going to the background, while it is still there, not only when it comes back (\dref{P71}; the check on return stays, as the system may pause timers). On Android~13 and later the app switcher shows no picture of the app. Older versions still show one, because hiding it there would also block the user's own screenshots (\dref{D53}). Settings offer ``Lock now''. \todo{iOS: exclude the vault from iCloud and device backups (\texttt{isExcludedFromBackup}), \dref{O9}}

\section{Synchronisation}
\label{sec:sync}

\begin{itemize}
  \item \textbf{Operations}: field-level last-writer-wins with hybrid logical clocks (\dref{P22}--\dref{P25}); deletions are tombstones.
  \item \textbf{Batches}: a device groups operations into batches with a header (suite, device identifier, per-device sequence number, clock range). The batch is encrypted under $K_{\mathrm{sync}}$ with the header as associated data and signed with the device's identity key (Ed25519 and ML-DSA-65).
  \item \textbf{Transport-agnostic}: the same encrypted batches move through peer-to-peer connections, files or the user's cloud storage, where each device writes only its own files.
  \item \textbf{Rollback and gaps}: per-device sequence numbers and signed checkpoints of the latest sequence numbers seen let devices detect missing or rolled-back batches. Withholding can be detected, not prevented.
  \item \textbf{Lost device}: another device signs a new device list without it and rotates $MK$ (\cref{sec:keys}).
\end{itemize}

\section{Adding a device}
\label{sec:pairing}

\begin{enumerate}
  \item The existing device shows a QR code with a 256-bit pairing secret $\sigma$ and connection hints.
  \item The new device scans it. Both run a key exchange in which the new device sends an X-Wing public key, the existing device encapsulates to it, and both derive $K_{\mathrm{pair}} = \KDF(ss \concat \sigma, \mathit{transcript})$. Key confirmation in both directions follows.
  \item The existing device sends $MK$ and the device list, encrypted under $K_{\mathrm{pair}}$; the new device adds its identity key, signed by the existing device.
\end{enumerate}
Because $\sigma$ is a symmetric secret, an attacker who later breaks X25519 still lacks $\sigma$; the X-Wing exchange adds forward secrecy. In the browser, this runs inside the WebRTC data channel, whose own encryption isn't quantum-safe. \todo{base it on a Noise pattern with a pre-shared key and a KEM; formal analysis in ProVerif or Tamarin}

\section{Sharing}
\label{sec:sharing}

\begin{itemize}
  \item \textbf{Share container}: each share has a random key $K_{\mathrm{share}}$ and contains only the selected records and fields (\dref{P27}).
  \item \textbf{Key delivery}: one HPKE stanza with X-Wing per recipient (\cref{sec:sealed}).
  \item \textbf{Manifest}: share identifier, selection, permissions (read or read-write, \dref{D18}), expiry and recipients, signed by the sender with the composite signature (\cref{sec:sealed}).
  \item \textbf{Read-write}: a recipient's changes are signed with their identity key; the owner's devices merge them only if the manifest allows those record types and fields.
  \item \textbf{Revocation}: a new $K_{\mathrm{share}}$ for the remaining recipients; revoked recipients keep what they already received.
  \item \textbf{Links for people without the app}: a random key in the URL fragment (never sent to any server), the ciphertext in the sender's own cloud storage (\dref{D24}).
\end{itemize}

\subsection{Sealed containers (format 1, proposal \dref{P88})}
\label{sec:sealed}
\emph{Research of 19 October 2026.} A sealed container carries one document of our JSON format family (\texttt{FORMATS.md} \S9) to its recipients, to a link, or into the user's own export: a training session, a plan, a meal plan, a set of measurements. The design follows age~v1 \cite{age}. It adds 256-bit keys, an inner signed envelope, padding, and rules for ongoing shares.

\paragraph{Why copies, not per-record keys.} A share never uses the vault's keys. It holds a copy of only the selected records and fields under a fresh key (\dref{P27}). That gives selection down to single fields and revocation per share, and no key leaves the device. 1Password's item links and Bitwarden Send share copies in the same way. Per-record keys in the vault would show the number and sizes of records at rest, and still couldn't leave out fields. Read-write spaces (\dref{D18}) get a space key and a journal of their own.

\paragraph{Keys.} Each container gets a fresh 256-bit content key $\mathit{CEK}$, from which two keys are derived:
\begin{itemize}
  \item $k_{\mathrm{hdr}} = \KDF(\mathit{CEK}, \str{sc-share/v1 header})$;
  \item $k_{\mathrm{pay}} = \KDF(\mathit{CEK}, \mathit{salt} = n_{\mathrm{pay}}, \str{sc-share/v1 payload} \concat \mathrm{SHA\text{-}256}(\mathit{header}))$, with $n_{\mathrm{pay}}$ 16 random bytes.
\end{itemize}

\paragraph{Header.} Text lines, as in age, so it can be inspected:
\begin{itemize}
  \item \texttt{sc-share/v1}. The version fixes every algorithm, and nothing is negotiated.
  \item One stanza per recipient. Stanzas name no recipient, so each recipient tries them. Post-quantum and classical recipients are never mixed (there are no classical types).
  \begin{itemize}
    \item \texttt{-> xwing} with $\mathit{enc}$ (1{,}120 bytes):
    \begin{itemize}
      \item HPKE base mode \cite{rfc9180} with the KEM MLKEM768-X25519 (\texttt{0x647a}, which is X-Wing \cite{hpkepq,xwingdraft}), HKDF-SHA256 and ChaCha20-Poly1305;
      \item \texttt{info} = \str{sc-share/v1 xwing}, empty associated data;
      \item the body is the sealed $\mathit{CEK}$ (48 bytes).
    \end{itemize}
    This is age's \texttt{mlkem768x25519} construction with our own label and a 256-bit key.
    \item \texttt{-> link} with a salt: the body is $\AEAD.\Enc(K_{\mathrm{link}}, \mathit{CEK})$, where $K_{\mathrm{link}} = \KDF(S, \str{sc-share/v1 link})$, or $\KDF(S \concat \Argon(\mathit{pw}), \ldots)$ with an optional password.
    \item \texttt{-> epoch} with a stream id and epoch $e$: the body is $\mathit{CEK}$ wrapped under $\KDF(\mathit{EK}_e, \str{sc-share/v1 epoch} \concat \mathit{stream\_id} \concat e)$ (ongoing shares, below).
    \item \texttt{-> pw-sk} and \texttt{-> recovery}, for exports to oneself: the passphrase together with the Secret Key, or the recovery key. Never the passphrase alone (\dref{P85}).
  \end{itemize}
  \item \texttt{---} and $\mathrm{HMAC\text{-}SHA\text{-}256}(k_{\mathrm{hdr}}, \mathit{header})$, over everything up to the mark. Each recipient checks it with the $\mathit{CEK}$ from its own stanza. So the MAC commits to one key, and recipients who accept a container all hold the same $\mathit{CEK}$ (against ``invisible salamanders'' \cite{albertini}).
\end{itemize}

\paragraph{Payload.} $n_{\mathrm{pay}}$, then the envelope in 64\,KiB chunks under $k_{\mathrm{pay}}$, with ChaCha20-Poly1305 \cite{rfc8439}:
\begin{itemize}
  \item the nonce is an 11-byte big-endian chunk counter followed by a final-chunk flag (age's STREAM \cite{stream});
  \item an overflowing counter is an error;
  \item nothing is compressed.
\end{itemize}

\paragraph{Envelope} (inside the encryption):
\begin{itemize}
  \item a 4-byte length and $\mathit{meta}$, JSON from our deterministic writer;
  \item a 4-byte length and the $\mathit{document}$;
  \item a 2-byte length and the signature;
  \item zero padding to the Padm\'e length of the whole envelope \cite{padme}, and at least 1\,KiB.
\end{itemize}
$\mathit{meta}$ holds:
\begin{itemize}
  \item the document's format and version;
  \item the sender's identity keys;
  \item the recipients' key fingerprints and roles;
  \item the creation time;
  \item for ongoing shares, $\mathit{stream\_id}$, $e$, $\mathit{seq}$, $\mathit{prev\_hash}$, the expiry, and a manifest (each item's id with the SHA-256 of its bytes, and deletions).
\end{itemize}

\paragraph{Signature.}
\begin{itemize}
  \item Composite ML-DSA-65 + Ed25519 \cite{compsig}, with keys used for nothing else.
  \item It signs $\str{sc-share/v1 sig} \concat \mathrm{SHA\text{-}512}(\mathit{header}) \concat \mathrm{SHA\text{-}512}(\mathit{meta}) \concat \mathrm{SHA\text{-}512}(\mathit{document})$, where the header includes its MAC.
  \item It sits inside the encryption, so storage never sees the sender.
  \item It covers the header, so a recipient can't re-encrypt a signed document to someone else (surreptitious forwarding \cite{davis}), and the recipient list is signed.
\end{itemize}

\paragraph{Checks, in this order.}
\begin{enumerate}
  \item Parse the header strictly, with limits on stanzas and sizes.
  \item Open a stanza.
  \item Verify the header MAC.
  \item Decrypt the payload and read the lengths.
  \item Verify the signature over the exact bytes.
  \item Check the sender against the contacts (a changed key is flagged, \dref{P28}), and check that we are among the recipients.
  \item Only then parse the JSON (I-JSON, with limits).
\end{enumerate}
Signatures and hashes cover the exact bytes, and nothing is re-serialized before it is verified. Our writer is deterministic, so JCS isn't needed.

\paragraph{Ongoing shares.}
\begin{itemize}
  \item A stream, with a random 128-bit id, has epochs. The key $\mathit{EK}_e$ of epoch $e$ reaches the members in a signed container with \texttt{xwing} stanzas.
  \item Each update has a fresh $\mathit{CEK}$ in an \texttt{epoch} stanza, so updates stay small; an \texttt{xwing} stanza costs about 1.2\,KB per recipient.
  \item $\mathit{seq}$ grows by one, and $\mathit{prev\_hash}$ chains the containers.
  \begin{itemize}
    \item A gap, a fork or a lower $\mathit{seq}$ is shown as an error, and an expired update as stale, as in TUF \cite{tuf}.
    \item The manifest lists all current items, so items can't be mixed from different versions.
  \end{itemize}
  \item Removing a member starts a new epoch. What they already received stays readable.
  \item Item ids in a share are $\mathrm{HMAC}(\mathit{EK}_{\mathrm{ids}}, \mathit{id})$ in UUID form, with one id key per stream: stable across updates, unlinkable between shares, and hiding the creation time that our UUIDv7 ids reveal.
\end{itemize}

\paragraph{Links} (\dref{P29}):
\begin{itemize}
  \item \textbf{The secret:} $S$ (32 random bytes) goes in the URL fragment, together with the container's address in the user's own cloud (\dref{D24}).
  \item \textbf{The viewer} is static:
  \begin{itemize}
    \item a strict CSP, Subresource Integrity and \texttt{Referrer-Policy: no-referrer};
    \item it removes the fragment from the address bar and history, and decrypts locally;
    \item links expire after a short time by default.
  \end{itemize}
  \item \textbf{The limit:} whoever serves the viewer's code could steal keys, and the app says so.
\end{itemize}

\paragraph{What leaks.}
\begin{itemize}
  \item The padded size.
  \item The number of stanzas. Dummy stanzas can't cheaply be made to look like X-Wing ones (unverified).
  \item For ongoing shares, when updates happen. Batching them, e.g.\ daily, hides activity.
\end{itemize}

\paragraph{Implementation.}
\begin{itemize}
  \item \textbf{Libraries} (19 October 2026):
  \begin{itemize}
    \item RustCrypto's \texttt{x-wing} 0.1.1 (draft~06, the same wire format as draft~11) has ``never been independently audited''; so have \texttt{ml-kem} 0.3.3, \texttt{ml-dsa} 0.1.1 and \texttt{hpke} 0.14 (per the research).
    \item libsodium 1.0.22 offers X-Wing, but no ML-DSA and no HPKE.
  \end{itemize}
  \item \textbf{The hybrid as a safety net:} the classical halves keep today's security even if the post-quantum code has a bug that leaks no keys.
  \item \textbf{Before sharing ships:}
  \begin{itemize}
    \item the drafts' test vectors (X-Wing, HPKE-PQ, composite signatures), age's vectors for the stanza construction, and Wycheproof;
    \item golden containers;
    \item fuzzing of both parsers;
    \item an external audit \todo{choose the library; audit}.
  \end{itemize}
\end{itemize}

\paragraph{Standards status} (19 October 2026):
\begin{itemize}
  \item \textbf{X-Wing} is draft-connolly-cfrg-xwing-kem-11, an independent submission and not an RFC \cite{xwingdraft}. The CFRG's hybrid-KEM draft calls the same construction MLKEM768-X25519.
  \item \textbf{HPKE-PQ} (draft-05) gives it the code \texttt{0x647a} and has no Auth modes \cite{hpkepq}.
  \item \textbf{The composite signatures} (draft-19) are in the RFC Editor's queue \cite{compsig}.
  \item \textbf{age 1.3} added the \texttt{mlkem768x25519} recipients \cite{age}.
  \item \textbf{COSE and JOSE} have no post-quantum HPKE yet. OpenPGP has it (RFC~9980, per the research), but it is much larger than we need.
\end{itemize}

\paragraph{Avoid.}
\begin{itemize}
  \item HPKE's Auth modes (dropped in the revision of RFC~9180; X-Wing has none), and treating a KEM as proof of the sender.
  \item Algorithm negotiation.
  \item Secrets in URL paths or queries.
  \item Re-serializing before verifying.
  \item Fields encrypted one by one without binding them together.
  \item Unaudited code without test vectors.
\end{itemize}

\section{Implementation and assurance}
\label{sec:assurance}

\begin{itemize}
  \item \textbf{Vetted libraries} behind the suite registry: RustCrypto for all of suite~1 in MVP~1 (\dref{D45}), pinned to exact versions; for the public-key parts that arrive with sync and sharing, libsodium (X-Wing, ML-KEM, Ed25519) and libcrux for ML-DSA (formally verified with hax and F*).
  \item \textbf{Checks implemented in M8}: \texttt{cargo deny} over both crates (known vulnerabilities in the RustSec database, licences, duplicate and wildcard dependencies, sources: only crates.io; on 23 October 2026 it flagged RUSTSEC-2026-0385, branches in \texttt{ctutils}' constant-time masks under the hash, MAC and Poly1305 crates, fixed by updating to 0.4.5, with a regression test on \texttt{Cargo.lock}); test coverage of the core, 96.8\,\% of lines; the app-level search of \cref{sec:ondisk}; a release check of the Android package (permissions, backup, debuggable, 16\,KB page alignment); the licences of all 105 compiled crates on the app's licence page.
  \item \textbf{Tests implemented in M2}: journal truncation at every byte, every flipped bit of a frame, gaps, repetitions and frames of other vaults, generations or devices; a golden journal file; merge property tests; crash points at every step of commits, compaction and storing files; the plaintext search of the previous section.
  \item \textbf{Tests implemented in M1}: through the core's own wrappers, draft-irtf-cfrg-xchacha-03 A.3.1 \cite{xchacha} and all 315 Wycheproof XChaCha20-Poly1305 tests \cite{wycheproof}; RFC 9106 §5.3 (Argon2id); RFC 5869 A.1--A.3 (HKDF-SHA-256); property tests (any changed bit, associated data or nonce is rejected); a golden keyring file; the tamper and crash tests of \cref{sec:keyring}; valgrind memcheck over the test binary.
  \item \textbf{Tests} (\texttt{CLAUDE.md}): official test vectors (NIST ACVP, Wycheproof) and our own known-answer tests for every format; a regression test for every fixed bug; fuzzing of all parsers (\texttt{cargo-fuzz}); Miri for any \texttt{unsafe} code; valgrind-based constant-time checks (e.g.\ ctgrind-style) and sanitizers.
  \item \textbf{Formal analysis} of pairing, sync and sharing (ProVerif or Tamarin) before launch; machine-checked implementations where feasible.
  \item \textbf{Independent audit} of the core, reproducible builds, a public vulnerability-reporting policy.
\end{itemize}
